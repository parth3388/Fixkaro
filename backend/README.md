# FIX-KAR Booking API

Production-oriented FastAPI backend for the existing FIX-KAR static
HTML/CSS/JS website. It powers the site's enquiry/booking form and the
"Track Service Request" page. The frontend itself was **not** rewritten —
see `BACKEND_ASSUMPTIONS.md` (alongside this file) for what was inferred
from it and why.

## 1. Project architecture

```
Browser (index.html / contact.html / track.html, script.js)
        │  fetch() JSON over HTTPS
        ▼
FastAPI app (this project)  ── Pydantic validation
        │  SQLAlchemy ORM
        ▼
PostgreSQL  (bookings / customers / services)
```

```
backend/
├── app/
│   ├── main.py              FastAPI app, CORS, error handlers
│   ├── core/
│   │   ├── config.py        Settings (env vars / .env)
│   │   ├── database.py      SQLAlchemy engine/session, Base
│   │   └── security.py      Booking reference generation, phone normalisation
│   ├── models/               SQLAlchemy ORM models (customer, service, booking)
│   ├── schemas/               Pydantic request/response models
│   ├── api/routes/            health.py, services.py, bookings.py
│   ├── services/               booking_service.py, service_service.py (business logic)
│   └── seed_data.py           Canonical service catalog, matches the frontend's <select>
├── alembic/                   Migrations (initial schema + service catalog seed)
├── tests/                     pytest suite (isolated SQLite, see BACKEND_ASSUMPTIONS.md)
├── requirements.txt
├── Dockerfile / docker-compose.yml   Local Postgres + API for development
├── .env.example
├── README.md                  (this file)
└── BACKEND_ASSUMPTIONS.md
```

No customer authentication, admin dashboard, payment integration, or SMS/
email provider is implemented — none of those exist in the current
frontend. See `BACKEND_ASSUMPTIONS.md` for the reasoning.

## 6. Environment variables

Copy `.env.example` to `.env` and fill in real values. **Never commit `.env`.**

| Variable        | Purpose                                                              | Example (dev)                                              |
|-----------------|-----------------------------------------------------------------------|--------------------------------------------------------------|
| `ENVIRONMENT`   | `development` or `production`                                        | `development`                                                |
| `DATABASE_URL`  | SQLAlchemy PostgreSQL connection string                              | `postgresql+psycopg2://fixkar:fixkar@localhost:5433/fixkar`  |
| `CORS_ORIGINS`  | Comma-separated list of frontend origins allowed to call the API     | `http://127.0.0.1:5500,http://localhost:5500`                |
| `SECRET_KEY`    | Reserved for future signed tokens (e.g. admin auth). Not used yet.   | any long random string                                       |

## 7. PostgreSQL setup

### Option A — Docker (recommended for local dev)

```bash
docker compose up -d db
```

This starts PostgreSQL 16 on **host port 5433** (mapped to 5432 in the
container) — 5433 is used instead of 5432 to avoid clashing with a
PostgreSQL instance that may already be installed natively on your machine.
If port 5432 is free on your machine, you can change the mapping in
`docker-compose.yml` back to `5432:5432` and update `DATABASE_URL`
accordingly.

Credentials (dev only): user `fixkar`, password `fixkar`, database `fixkar`
— set in `docker-compose.yml`'s `environment:` block.

### Option B — A PostgreSQL server you already run

Create a database and role yourself, e.g.:

```sql
CREATE USER fixkar WITH PASSWORD 'fixkar';
CREATE DATABASE fixkar OWNER fixkar;
```

Then point `DATABASE_URL` at it.

## 8. Alembic migration commands

```bash
# Apply all migrations (creates tables + seeds the service catalog)
alembic upgrade head

# Roll back everything
alembic downgrade base

# After changing a model, generate a new migration
alembic revision --autogenerate -m "describe the change"

# Check the currently applied revision
alembic current
```

The initial migration (`alembic/versions/0001_initial_schema.py`) was
generated with `--autogenerate` against a real PostgreSQL database and then
hand-verified, including a fix for a real Alembic/Postgres gotcha: the
autogenerated `downgrade()` dropped the `bookings` table but not the
Postgres `booking_status` ENUM type it depended on, which broke a
repeated `upgrade` → `downgrade` → `upgrade` cycle. The migration now
explicitly drops the enum type on downgrade — verified locally with three
consecutive upgrade/downgrade cycles against Postgres in Docker.

## 9. Running locally

```bash
# with the venv activated, from backend/
uvicorn app.main:app --reload --port 8000
```

The API is then available at `http://localhost:8000`, matching the
`API_BASE` the frontend's `script.js` uses for `localhost`/`127.0.0.1`.

To run backend **and** Postgres together with Docker:

```bash
docker compose up --build
```

(`docker-compose.yml`'s `api` service runs `alembic upgrade head` on start,
then `uvicorn --reload`.)

### Serving the frontend against it

The frontend is unchanged static HTML — serve it however you already do

`CORS_ORIGINS` defaults to). `script.js` auto-detects local development and
points `fetch()` calls at `http://localhost:8000/api/v1`.

### Endpoints

| Method | Path                                   | Purpose                                   |
|--------|------------------------------------------|---------------------------------------------|
| GET    | `/api/v1/health`                         | Health check                                |
| GET    | `/api/v1/services`                       | List active service categories              |
| GET    | `/api/v1/services/{slug}`                | Get one service by slug                     |
| POST   | `/api/v1/bookings`                       | Create a booking (the enquiry form)         |
| GET    | `/api/v1/bookings/{booking_reference}?phone=` | Track a booking (requires the phone it was booked with) |
| POST   | `/api/v1/bookings/{booking_reference}/cancel` | Cancel a booking (body: `{"phone": "..."}`) |

Every response is `{"success": true, ...}` or, on error,
`{"success": false, "error": {"code": "...", "message": "..."}}`.

## 12. Production deployment overview

```
Internet → Domain (HTTPS) → Nginx → Gunicorn (Uvicorn workers) → PostgreSQL
                                   ↘ static files (the existing HTML/CSS/JS)
```

Run the API with Gunicorn managing Uvicorn workers (not `uvicorn --reload`,
which is dev-only):

```bash
gunicorn app.main:app -k uvicorn.workers.UvicornWorker \
  --workers 4 --bind 127.0.0.1:8000
```

The app binds to `127.0.0.1:8000` — **never expose port 8000 directly to
the internet**; only Nginx (on 80/443) is public-facing.

## 13. Nginx configuration overview

The canonical config lives at
[`backend/deploy/nginx/fixkaro.conf`](deploy/nginx/fixkaro.conf) — copy that
file rather than retyping the block below; this section just explains it.

It does three things:

1. Reverse-proxies `/api/v1/` to the FastAPI/Gunicorn process.
2. Serves the static frontend from `/var/www/fixkaro` (the real path the
   deploy workflow's `rsync` step writes to — see `.github/workflows/deploy.yml`).
3. Routes extensionless URLs (`/services`) to the matching `.html` file on
   disk via `try_files`, and 301-redirects a direct `/services.html` request
   to its canonical `/services` URL (`/index.html` → `/`).

```nginx
server {
    listen 80;
    server_name fix-kar.in www.fix-kar.in;

    root /var/www/fixkaro;
    index index.html;

    # FastAPI backend — must resolve before the static "/" block.
    location /api/v1/ {
        proxy_pass http://127.0.0.1:8000/api/v1/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location = /index.html {
        return 301 /;
    }

    location ~ ^/([a-z0-9-]+)\.html$ {
        return 301 /$1;
    }

    location / {
        try_files $uri $uri.html $uri/ =404;
    }
}
```

With this setup, `script.js`'s production branch (`/api/v1`, a relative
path — see §15) works without any further frontend changes. Put a real TLS
certificate (e.g. via Certbot/Let's Encrypt) in front of this in production.

### One-time activation (manual — not run by CI)

The deploy workflow's self-hosted runner already has `sudo` for `rsync` and
`systemctl`, but it does **not** touch Nginx's own config — that's
deliberate, since a CI step guessing at your existing `sites-available`
filename could silently no-op or break a working deploy. Apply this once,
by hand, on the EC2 instance:

```bash
sudo cp /home/ubuntu/Fixkaro/backend/deploy/nginx/fixkaro.conf /etc/nginx/sites-available/fixkaro
sudo ln -sf /etc/nginx/sites-available/fixkaro /etc/nginx/sites-enabled/fixkaro
sudo nginx -t
sudo systemctl reload nginx   # not `restart` — and never reboot the instance for this
```

After that, every future `git push` to `main` only needs to update the repo
file (`backend/deploy/nginx/fixkaro.conf`) and repeat the `cp` + `nginx -t`
+ `reload` above if you change it — the app deploy itself doesn't touch
Nginx.

## 14. AWS EC2 deployment steps

> **Note:** this section is the from-scratch bootstrap guide for a new
> environment. The live fix-kar.in environment already exists and redeploys
> automatically via `.github/workflows/deploy.yml` on every push to `main`
> (a self-hosted runner on the instance itself: repo at
> `/home/ubuntu/Fixkaro`, static files rsynced to `/var/www/fixkaro`,
> backend run as the `fixkaro` systemd service). Steps 1–3 and 8 below don't
> apply there — only Nginx (§13's one-time activation) is outside that
> pipeline.

1. **Launch an EC2 instance** (e.g. Ubuntu 22.04 LTS, t3.small or larger).
   Security group: allow inbound 22 (SSH, restricted to your IP), 80, 443.
   Do **not** open port 8000 or 5432 to the internet.
2. **Install system dependencies:**
   ```bash
   sudo apt update
   sudo apt install -y python3.11 python3.11-venv postgresql nginx
   ```
   (Or run PostgreSQL as a managed service, e.g. Amazon RDS — recommended
   for production so the database survives independently of the EC2
   instance. Point `DATABASE_URL` at the RDS endpoint instead.)
3. **Create the database and role** (§7 Option B) if self-hosting Postgres
   on the instance, or create the RDS instance/database if using RDS.
4. **Deploy the code:** `git clone`/`scp` this repo's `backend/` directory
   to the instance, e.g. into `/opt/fixkar/backend`. Deploy the existing
   frontend files to `/var/www/fixkaro` (§13's Nginx `root`).
5. **Set up the virtual environment and install dependencies** (§4–5) on
   the instance.
6. **Create `/opt/fixkar/backend/.env`** with production values (real
   `DATABASE_URL`, `CORS_ORIGINS=https://fix-kar.in,https://www.fix-kar.in`,
   `ENVIRONMENT=production`, a freshly generated `SECRET_KEY`). Restrict its
   file permissions (`chmod 600 .env`).
7. **Run migrations:** `alembic upgrade head`.
8. **Run the API as a systemd service** so it restarts on boot/crash.
   Example `/etc/systemd/system/fixkar-api.service`:
   ```ini
   [Unit]
   Description=FIX-KAR FastAPI backend
   After=network.target

   [Service]
   User=fixkar
   WorkingDirectory=/opt/fixkar/backend
   EnvironmentFile=/opt/fixkar/backend/.env
   ExecStart=/opt/fixkar/backend/.venv/bin/gunicorn app.main:app \
       -k uvicorn.workers.UvicornWorker --workers 4 --bind 127.0.0.1:8000
   Restart=always

   [Install]
   WantedBy=multi-user.target
   ```
   ```bash
   sudo systemctl enable --now fixkar-api
   ```
9. **Configure Nginx** with the server block from §13, then:
   ```bash
   sudo nginx -t && sudo systemctl reload nginx
   ```
10. **Enable HTTPS** with Certbot: `sudo certbot --nginx -d fix-kar.in -d www.fix-kar.in`.
11. **Verify:** `curl https://fix-kar.in/api/v1/health` and load the site
    in a browser, submit the enquiry form, and confirm a booking reference
    appears.

## 15. Connecting the frontend to the production API

No frontend code changes are needed beyond what's already in this repo.
`script.js` resolves the API base URL as:

```js
const API_BASE =
  location.hostname === "localhost" || location.hostname === "127.0.0.1"
    ? "http://localhost:8000/api/v1"
    : "/api/v1";
```

In production the site is served from the real domain (not `localhost`), so
it automatically uses the relative path `/api/v1`, which Nginx proxies to
the backend (§13). If the API is ever hosted on a **different** domain than
the frontend, change the second branch to that absolute URL, e.g.
`"https://api.fix-kar.in/api/v1"`, and add that frontend origin to the
backend's `CORS_ORIGINS`.
